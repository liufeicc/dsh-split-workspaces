# dsh-split-workspaces

本地 DSH 插件包：在 Harness Web 界面的主面板里把多个工作区**上下左右平铺**，
每个窗格一个工作区对话，分隔条可拖动改尺寸、标题栏可拖动交换两格位置，
当前获得焦点的窗格用品牌色标题栏标出。

## 它加了什么

- 侧边栏的一行图标（两个平铺格子，紧邻 Plugins 图标），点它把主区切到
  **多工作区平铺**面板。
- 面板本身：顶部只有标题和 `添加工作区`，下面是棋盘 —— 每个窗格都有
  自己的标题栏（工作区名与路径、`打开目录` 图标、`分屏` 图标、模式选择、MCP 开关、会话选择、关闭），
  窗格内部复用共享的 `conversation.content` Factory（`embedded` 变体），挂在显式的
  `SessionProvider` 绑定下，因此每个窗格都是一个完整对话（记录、输入框、流式输出）。
- **每格的会话视图标签栏**：每个窗格的对话区上方会自动列出当前注册的 `conversation.view`
  —— 默认是“对话”；装了 Git 面板就是“对话 / Git”。**“轨迹”只在主对话里提供，平铺窗格
  固定不列它**。标签栏只读框架的注册表，不复制任何插件自己的界面；点 Git 就是 Git
  插件原本的面板。每格独立选择、默认对话；**没装额外视图插件（或只有 Chat）时
  不渲染标签栏**，窗格行为与改造前完全一致。
- **保存布局 / 自动恢复**：右上角的保存图标按当前面板模式**分部分保存** ——
  平铺模式只写棋盘（分屏方向、比例、窗格顺序、焦点）与每格的会话/Agent 模式；
  任务分派模式只写**分派图（边 + 说明 + 已拖入但还没连线的节点）**。另一部分保留**上一次保存的内容**，
  不会被这次保存清空。保存结构不记录面板模式：刷新后固定从平铺模式开始。
  **已经拖进画布的空白会话**不受「每个工作区只显示最新一条」的限制，保存时也不会被筛掉
  —— 即使用户之后又新建了一张空白会话，画布上原有的待连线卡片仍然保留。
  保存记录落在 Host 的 `$DSH_HOME/storages/pane_layout.json`；页面重新加载后
  第一次进入平铺面板时自动恢复，同一次页面内切换面板不会覆盖当前实时布局。
  恢复时缺工作区/会话/模式/分派边都静默丢弃或回退，不报错。模型本身按会话
  持久化，恢复会话即恢复当时的模型，不另存一份模型快照。
- **`打开目录` 图标**（工作区名右边那个文件夹）：点它把**这一格**的工作区目录交给
  系统文件管理器（Linux 的 `xdg-open`、macOS 的 Finder、Windows 的资源管理器）。
  它没有自己实现这套东西，而是复用已经装好的 Session 远端命名空间
  （`@deepseek-ai/dsh-api-session-controller`）那两个方法：
  `canOpenWorkspacePath()` 先回答「这个部署能不能把路径交给桌面」（没有图形环境的
  Linux 容器答 false，那正是「你面前没有文件管理器」的意思），`openWorkspacePath({ path })`
  再在组合文件系统里**校验**这个路径确实是 Host 上能打开的目录，然后按操作系统的关联
  打开它 —— 目录的关联就是文件管理器。于是「用哪条命令打开」只有一份实现、一套校验，
  本插件也不必在 Host 上加一行、不需要用户重启。
  可用性是部署级事实，只问一次；目录不在 Host 映射里、文件管理器起不来、这个部署
  没有会话服务、压根没有图形环境，都在窗格自己的错误行里说清（本地化原因在前，
  Host 的原文当细节附在后面）。
- **`替换工作区` 图标**（每格标题栏各一个，夹在「打开目录」与「分屏」之间）：把**这一格**
  换成另一个工作区，或同一个工作区的另一个会话。菜单是**两级**：
  第一级是 `新建工作区…`（复用同一个文件夹选择器与注册流程）加**全部**工作区
  （包括已经铺在别的格子里的，已铺开的标「已打开」），按侧边栏顺序排；
  第二级是这个工作区的会话列表，第一条固定是「新建会话」，下面是它已有的会话。
  选中已有会话时**位置不变**：布局树、分隔条比例、与邻居的关系一个字节都不动，
  这一格原子地换成「新工作区 + 这个会话」，并把会话钉住（同一个会话开在别的格也允许）；
  选「新建会话」时会先弹选择框：**新建会话**（普通会话，优先复用该工作区里没被别的
  窗格钉住的空白会话，没有才真的新建）或**新建目标**（为派单强制创建一个**全新的**
  空白目标，绕过平台的空白会话复用；创建即存入 Host 的目标清单，刷新后仍在；与普通
  新建一样立刻进入当前窗格，看到输入框）。两者都会把这一格暂存的 Agent 模式带上。
  已经铺开的工作区也在候选里，因为「同一个工作区换一个会话」是合理用法；真要对调
  两格位置仍用拖动标题栏那条路。
  做成「每格一个图标」而不是面板顶部一个按钮，是为了永远不必回答「替哪一格」。
- **`切换会话` 下拉里每一行都有一个删除按钮**（行尾的垃圾桶图标）：点它永久删掉**那一行**
  的会话 —— 不必是这一格当前正显示的那一个，而这正是做成「逐行」而不是「菜单底部一个按钮」
  的理由：菜单里摆的就是一列会话，想清的往往正是**别的**那一行，底部一个按钮会让人先去推理
  「它删的是哪一个」。删除本身不在本插件里实现：本插件把「哪一行、叫什么名字」交给
  `dsh-session-delete` 已经装好的**确认弹窗**（该插件的客户端半边用 `ctx.provide` 发布的
  `sessionDeleteUi` 服务，本插件在点击时用 `ctx.get` **惰性解析**，与 MCP 策略那条路同款）。
  于是确认、「会话正在运行就先停下来再删」、删完通知会话列表这几件事都只有一份实现。
  删成功后本插件把**所有**钉着这个会话的窗格一起松手（同一个会话可能同时显示在好几格上 ——
  跟随型窗格会自动选中本工作区最新的真实对话）：跟随型窗格随即回退到本工作区最新的
  真实对话，用户亲手选过会话的分屏窗格回到「选择会话 / 新建会话」的空态。没装
  `dsh-session-delete` 时按钮照样在，点一下会在窗格错误行里明说「删除会话失败：……删除服务」，
  而不是假装删掉了。
- **平铺方式**：`添加工作区` 总是把新窗格接到整块棋盘的右边；每个窗格标题栏上的
  **分屏菜单是两步**：第一步选方向（向左、向右、向上、向下），第二步选**要放进新窗格的
  工作区**。选完方向不会立刻分屏，也不会顺手把当前窗格的工作区再开一格 ——
  平铺的意义就是把**不同**工作区摊开看。于是任意组合都能拼出来，
  例如「上排两个并排、下排一个」= 先把 A 向下分（选 C），再把 A 向右分（选 B）。
  第二步里除了列出现有工作区，还有一行 `新建工作区…` 可以直接挑一个新目录。
  一个图标按钮加两段菜单，比排四个按钮更省标题栏宽度。
- **拖动改尺寸**：窗格之间是一条可拖动的分隔条，左右布局就左右拖，上下布局就上下拖；
  双击分隔条恢复均分，聚焦分隔条后按方向键可微调（按住 Shift 步长更大）。
  比例按「占容器的百分比」保存，因此窗口缩放后布局比例不变。
- **拖动标题栏交换位置**：按住窗格标题栏（里面的按钮、下拉、菜单面板除外）拖到**另一个窗格**上
  松手，两个窗格就交换位置。拖动途中只有落点那一格亮起强调色圈、被拖的那格淡出，
  **松手才交换**；落在空白处松手什么都不做。它换的是**位置**不是内容：两格各自的工作区、
  会话、预选模式都跟着自己走，因此高亮与键盘光标也跟着被拖的那一格去到新位置
  （交换后光标会等一帧重新安放进它的输入框，理由与「关窗格要等一帧」同源）。
  移开不到 4 像素的按下仍然算**单击**（点亮窗格、送光标），于是标题栏依旧是「点一下聚焦」的把手。
  没有 Esc 取消、没有拖到边缘分屏、没有键盘交换 —— 那几条都是「松手才交换」之外的额外语义。
- **焦点高亮**：在哪个窗格里按下鼠标或按 Tab 进入，那一个窗格就成为当前焦点 ——
  只有它的**整条标题栏是蓝色渐变 + 白字**（工作区名、路径、模式/会话触发器、按钮一起变白），
  窗格本身仍是和其他窗格一样的细边框，不加高亮框、不加外发光；
  关掉焦点窗格时，焦点自动交给顶替它位置的那个窗格。
- **键盘光标跟着高亮走**（一条不变量，两个方向都要成立）：窗格被点亮时，光标也进它的输入框；
  反过来，用户点在窗格里的**控件**上（标题栏按钮、下拉、消息里的复制按钮、链接、输入框本身），
  光标就留在那儿，绝不抢。少了前半条会出很难自查的错 —— 点开右边窗格的消息区、以为在跟它说话，
  打出来的字却进了别处；少了后半条会毁掉标题栏的键盘可达性与弹出菜单。
  用户刚拖选出一段文字时也一个字都不碰（`focus()` 会把那段选区整段抹掉，见坑 5）。
  关掉当前窗格时，顶替它的窗格在**下一次重排之后**接管光标（它会重新挂载，理由同样在坑 5）。
  窗格里没有可打字的输入框时（还没会话、宿主 inert），只切高亮、不动光标。
- **弹出菜单挂在 `document.body` 上**：窗格是 `overflow:hidden`，菜单如果留在窗格 DOM 里，
  窗格一窄就会被裁掉（标题栏的模式 / 切换工作区 / 分屏 / MCP / SKILL 都受影响）。
  所以菜单用 portal + `position:fixed`，按触发器的位置左右夹取、下方放不下时向上翻转，
  高度按视口限制并内部滚动。代价是菜单会盖在相邻窗格上面 —— 这是弹出菜单的正常行为。
  渐变两端是把蓝色强调色与静态黑 token 混出来的（`color-mix`），既做出图里那种由深到浅的
  蓝，也把白字的对比度抬到 4.5:1 以上 —— 纯强调色配白字只有 3.3:1，偏糊。
  离线测试会把渐变逐端算一遍对比度，低于 4.5:1 直接判失败。
  焦点标题栏上的按钮（分屏图标、模式/会话下拉、关闭）在 hover / 展开时用的是**黑色压深**，
  而不是拿白色调淡：白字配「白 24% 压出来的浅灰蓝底」只有 3.5:1，看着就是一块灰底、字糊在
  上面；改成黑底后 hover 是黑 50%（底仍透出一点蓝）、展开是纯黑，同一处白字分别有 11:1 与
  21:1，离线测试同样逐端算一遍。
- **`Alt+方向键` 搬焦点**：按 `Alt+←/→/↑/↓` 把焦点交给**那个方向上相应位置**的窗格，
  并把键盘光标一起送进它的输入框（于是切过去就能直接打字，全程不用碰鼠标）。
  方向按窗格的**矩形**判定，不是按布局树的嵌套关系：候选必须整个在那个方向之外，
  且垂直方向上有重叠；距离近的优先 → 重叠多的优先 → 中心更对齐的优先。
  于是「上排 A|B、下排 C|D」里 A 按 `Alt+↓` 只会到 C（D 与 A 一行重叠都没有），
  「A | X | B」三连排里 A 按 `Alt+→` 先到紧挨着的 X 而不是跳过它。
  走到最边上再按**不动**（不绕回对面）：循环会让人在满屏窗格之间迷失方向。
  这四个键位同时登记进框架的快捷键名册，因此能在 **设置 → 快捷键** 里看到，
  也不能再被分配给别的命令。
- **下拉菜单面板的底色**用「抬升表面」`--dsw-alias-bg-layer-2`（深色 #2c2c2e / 浅色 #fff），
  不用 `--dsw-alias-bg-overlay` —— 后者在深色主题里是 #61666b 的中灰，面板上白字只剩 5.6:1、
  次要文字（「当前」「当前会话已开始…」）只有 3.9:1。换底色后深色主题下分别是 13.3:1 与
  9.3:1。连带把菜单项的 hover 从 `bg-layer-2` 换成 `currentColor 8%`：面板自己就是
  `bg-layer-2`，再拿它当 hover 底等于按下去没反应。
- **每个窗格独立的 Agent 模式选择器**（标准 / PTC / 极简 / 创造，外加自定义预设）：
  和侧边栏新建任务用的是同一份 Host 花名册（`remote.agentPresets.list`），
  既标出窗格当前会话运行的模式，也标出为下一个会话预选的模式。
- **按工作区共享的 MCP 工具开关**（标题栏上的 `MCP` / `MCP n` 下拉）：勾选哪些 MCP
  服务器的工具对这个工作区可见。它与模式选择器的语义**正相反** —— 模式是「按窗格暂存、
  按会话生效」，而 MCP 可见性是宿主按**会话 cwd** 施加的策略，因此同一工作区的所有会话
  共享同一份选择。清单与工具数来自 Host（`remote.mcpWorkspace.list`，服务器名从工具名
  `mcp__<server>__*` 自动发现），勾选走 `set`：宿主立刻重挂工具限制并落盘。
  未配置的工作区**默认全不选**，也就是完全不暴露 MCP 工具、不占上下文。
- **按工作区共享的 SKILL 开关**（标题栏上的 `SKILL` / `SKILL n` 下拉）：勾选技能库里哪些
  技能对这个工作区可见。它与 MCP 开关是**同一个形状**（都是宿主按工作区施加的策略），
  差别在开关项来自**技能目录自身的扫描结果**，所以每一行都带得出技能描述 —— 不看描述
  根本没法选。技能目录为空、目录不存在、某个技能文件写坏了，弹层里分别说清是哪种情况：
  只给一片空白会让人一直在猜「是我没建文件，还是插件没生效」。技能目录本身由
  「设置 → 技能」维护，本块只读它，唯一会写的是某个工作区的勾选集合。
  技能库插件的客户端半边没挂上时，标题栏**不出现**这个按钮，而不是给一个点了没反应的。
- `添加工作区` 的下拉菜单会列出「还没铺开的工作区」，也支持从文件夹选择器
  （`uiWorkspace.pickDirectory()`，或在 Desktop 下走 preload 桥）**新建**一个工作区。
  同一条「选目录 → 注册工作区」的实现也供分屏菜单第二步的 `新建工作区…` 使用，
  因此两处只会有一套选择器与一套失败处理。

- **设计模式 + 任务分派**：面板顶部多一个 `设计`，把每个**会话**画成卡片、用箭头连成
  一棵有向树 —— 箭头方向就是授权方向，删掉箭头等于撤回授权。连了箭头的会话会拿到
  **作用域版** `dispatch_task`、`report_task`、`consult_task` 与 `control_task` 工具
  （描述里直接列出可派目标）：
  `dispatch_task` 把任务交给对方会话并拿回结论，一次可派给多个目标、并行推进，支持
  「等全部 / 等第一个 / 派完就走」三种收尾，派完就走的还会在回合结束前被提醒回来收结果；
  `report_task` 则按 A 的要求，让目标基于自己的模型可见历史做一次**只读汇报**，
  不改目标、不创建 goal、不产生交付结论；`consult_task` 把问题**真正投递**进目标会话，
  目标用自己的工具查文件/跑命令后回答，不建 goal、不进入审核；`control_task` 用来中途停住
  （等目标真正 idle、暂停）或唤醒暂停的原目标。每次结果还会附上其余空闲目标，提示继续分配；
  交付后必须先审核，才能给同一个目标派新任务。详见下面的专节。

- **图片编辑入口**：平铺模式的标题栏与任务分派画布顶部各有一个「图片编辑」按钮
  （需要安装 `@local/dsh-image-editor`；没装时按钮不渲染）。点击后在 `shell.overlay`
  上打开浮动画布 —— 可直接画图，或粘贴截图在上面标注，然后复制回对话或保存 PNG。
  浮窗与左侧栏的整页面板共用同一份画布内容，平铺界面不会因此卸载。

## 设计模式：把委派关系画成箭头

面板顶部有两个模式：**平铺模式**（默认，就是上面讲的那一切）与**任务分派**。任务分派
从左侧选择器把**会话**拖成卡片，卡片之间用箭头连成一张**有向树** —— 箭头方向就是委派方向：

```
   ┌───┐      ┌───┐
   │ A │─────▶│ B │
   └───┘ ╲    └───┘
          ╲   ┌───┐
           ╲─▶│ C │
              └───┘
```

读法是「会话 A 可以把任务派给会话 B，也可以派给会话 C」。这张图**就是**授权关系本身 ——
没有第二份配置，删掉箭头就是撤回授权。

### 怎么画

- **连一条**：按住卡片右边缘那个圆点，拖到另一张卡片上松手。
  拖动途中有一条虚线跟着指针，松手落在空白处则什么都不做。
- **删一条**：点箭头中点那个小叉。
- **看内容**：点卡片打开这个会话的浮动窗口，可拖动、可输入，不会离开任务分派画布。

### 两条不变量（为什么是「树」）

1. **不许成环**：A→B→A 没有任何意义，直接拒绝。
2. **每个会话最多一个上级**：`A→B`、`A→C` 都成立（A 有两个孩子），但 `A→C`、`B→C`
   不允许（C 只能有一个上级）。这条是「树」与「一般有向图」的分界，也保证了布局永远
   是「根在左、下级往右」，箭头不会往回画。

被拒绝时画布底部直接说原因（成环 / 对方已有上级 / 这条已经有了）。

### 卡片就是会话，不是窗格

这一条**改过一次**。第一版把卡片绑在窗格 key 上，理由是「你说这一格派给那一格，指的就是
屏幕上那一格」。真用起来立刻露馅：

- 同一个会话开在两格里 → 两张卡片，连哪张都说不清；
- 关掉窗格 → 关系跟着消失，可「谁能派给谁」跟窗口开没开没有关系；
- 换掉某格的会话 → 关系悄悄跟到了新会话身上；
- **没在棋盘上打开的会话永远连不出箭头**（真机联调就撞了这个，A 连着失败四次）。

现在节点是**会话 id**：箭头记的是「会话 A 可以把任务派给会话 B」，与它在哪个窗格、
有没有窗格都无关。

- **候选范围**：**全部已存在的会话**（归档会话、子代理会话不算；**带目标记录的空会话算**
  —— 可以先建目标、再连线派活；普通空白会话也收**最近更新的一条**），不限于当前铺在
  棋盘上的工作区 —— 委派关系是会话之间的事，跟哪个工作区开着没关系。
- **左侧二级选择器**：画布不再平铺全部会话。左栏按工作区分组（组按字母排序，默认折叠），
  点开一个工作区后才列出它的会话；把会话卡片拖到右侧画布（或点一下）即可加入。
  **每个工作区行右侧都有两个入口**：`创建会话`（复用本工作区已有的空白会话，没有才新建）
  与 `创建员工`（强制新建一条空白会话并登记成派单目标）；创建后自动展开该工作区。
  **没有会话的工作区也保留组行**，否则新图标没有地方可点。
  **已经加入画布的会话会从左侧列表消失**，移出画布后才重新出现。拖进来的卡片先停在画布
  左侧的「待连线」列（虚线边框），连上箭头后才进入右侧的树；删掉箭头又回到待连线。
  不属于任何工作区的**有内容**会话归入「未归属工作区」，固定排在最后。普通空白会话显示为
  「未命名会话」；带目标记录的显示为「未命名员工」—— 目标开始对话或被派单后，显示真实标题。
  **用户改过名的会话一律显示新名字**，即使它还是空白会话（否则改完名看起来像没生效）。
  **每张卡片右上角都有删除按钮**（普通会话、空白会话、员工目标一视同仁），
  **已经有标题的卡片还多一个改名铅笔**：
  - 铅笔打开改名弹层，改的是**会话标题**（走平台的重命名，Host 会归一化并把名字钉住），
    刷新/重启后仍然是新名字；会话内容与箭头都不受影响。左侧选择器与画布卡片用的是
    同一个弹层，两处名字永远一致。
  - **未命名会话 / 未命名员工没有铅笔**：它们还没有标题，平台会把标题回退成目录名或
    占位名，改了也显示不出来。动作层同样会拒绝绕过界面的调用 —— 先开始一段对话、
    有标题之后再改名。
  - 垃圾桶走平台的删除确认框；删除目标时会同时清掉目标记录和牵涉的箭头。
- **收起左侧栏**：点「会话节点」标题右侧的 `‹` 把整栏收起，画布占满；画布左上角的
  `›` 再展开。收起状态只作用于当前页面，切换模式或刷新后恢复展开。
- **拖入后连线**：画布上的卡片仍然按住右侧光点拖到另一张卡片上建立关系；待连线卡片右上角
  的 × 可以把它移出画布。
- **卡片状态**：每张卡片显示这个会话自己的目标状态（目标进行中 / 已暂停 / 受阻 / 已完成）
  和审核状态（待审核 / 等待审核），**与它有没有连线无关**。状态由 Host 合成，任务分派
  模式下每 1.5 秒刷新一次。
- **浮动窗格**：点卡片打开该会话的浮动窗口，可以拖动位置、同时开多个。窗口保留输入、
  目标条、模式 / MCP / SKILL、标签栏等操作；**会话名只作静态显示，不能切换**，
  替换工作区、分屏、标题栏关闭图标都不提供（关闭走浮窗顶部条）。四条边和四个角都能
  拖动改变大小（顶部条最上面几条像素用于向上缩放，条体本身用于移动）。浮窗可以互相
  重叠；点任意位置——**包括标题栏**——都会把那一张提到最上层，最上层的浮窗边框显示
  金色，其余保持青色。浮窗不写进保存布局，切回平铺模式时自动关闭。
- **多棵树整块堆叠**：画布上同时存在几棵互不相连的树时，每棵树作为一个整体垂直排列，
  第二棵树从第一棵树最底边之下开始，箭头与说明不会互相穿插。
- **按来源取色**：同一个工作区的卡片、同一条源会话发出的箭头用同一种霓虹色；连接线上
  叠了一层沿箭头方向流动的高光。
- **会保存**：箭头存在 Host 上（`~/.dsh/storages/pane_dispatch_bindings.json`），
  刷新页面、重启 Host 都还在。客户端启动时读回来把树重建出来 —— 不需要另外存一份图，
  绑定表本身就是那棵树。
- **关窗格不清箭头**；只有会话被删除时才清掉它牵涉的边。
- **点卡片**打开浮动窗口；同一个会话已经开着浮窗时只把它提到最上层。

### 模型怎么用

A 的模型多了 `dispatch_task`、`report_task`、`consult_task`、`control_task` 四个工具：
`dispatch_task` 派活，`report_task` 只读汇报，`consult_task` 真投递咨询，
`control_task` 停止或唤醒。下面先说派单。

派单和汇报只针对**下属**：标题含「专家」「顾问」等字样、或连接线描述明确说可以咨询的会话，
不派活、也不要求汇报；有问题用 `consult_task` 咨询。

| 参数 | 说明 |
|---|---|
| `task` | 任务正文。对方看不到 A 的历史，背景与**可检验的验收标准**都要写清。续等时省略；目标正在跑时给 `task` 表示**纠正**（先停止当前轮，再把纠正作为新消息重新提交，并重新启动目标；不新建目标） |
| `targets` | 派给哪些目标（数组）。每项可用序号、完整标题、标题片段或会话 id。可派目标多于一个时必须指明；不给 `task` 时省略它表示接着等所有还在跑的目标 |
| `wait` | `all`（默认，等全部）/ `any`（第一个目标进入终态就返回，可能是完成/失败/暂停，其余留到下次）/ `none`（不等） |
| `reviews` | 审核上一单的交付结论（数组，每项 `{ target, verdict: accepted \| rejected, note? }`）。与 `task` 互斥，必须单独调用；驳回必须写 `note`。见下面「交付之后」一节 |

返回的是**一批**结果：

| 字段 | 说明 |
|---|---|
| `status` | `dispatched` / `running` / `complete` / `partial` / `interrupted` / `failed` / `cancelled` / `redirected` / `reviewed` |
| `results` | 每个目标一行 `{ target, status, deliverable, reply, progress, interruptedBy, note }`，按请求顺序排 |
| `stillRunning` | 还有几个没结束 |
| `note` | 下一步该做什么（接着等 / 复核 / 先处理失败 / 等用户） |

**只有 `deliverable: true` 的 `reply` 才是交付结论。** `running` / `blocked` / `paused` /
`interrupted` 等状态的文本放在 `progress` 里，并明确标注「过程稿，可能被后续推翻」；
`interruptedBy: "user"` 表示用户手动停止了目标。

一次调用分五步：

1. **分流**：给了 `task` 且目标是空闲的 → 新派；没给 `task` → 续等；给了 `task` 且目标
   正在跑 → **纠正**（先停止当前轮，再作为新消息重新提交，并重新启动目标；不新建目标）；
   目标刚被用户手停 → 拒绝并让 A 先取走中断说明；
2. **预检**：新派的目标**全部**查忙闲，有一个在忙就整批一个都不派；
3. **建目标**：走 `goals.create` 把任务设成对方会话的**目标** —— 对方在目标模式下持续推进，
   而不是回一句话就结束。对方若有 `blocked`/`paused` 的旧目标，会先清掉（保留墓碑与历史）；
4. **等待**：按 `wait` 语义收尾；`none` 则挂一条后台监视、立刻返回；
5. **整形**：按请求顺序列出每个目标的结论，并给出下一步提示。

长任务不会被误判失败：每次调用最多等 5 分钟一段，到点带着**当前过程稿**返回 `running`
（`deliverable: false`，内容明确标注「过程稿，可能被推翻」），模型再调一次（省略 `task` 与
`targets`）接着等。过程稿可以用来判断方向，也可以据此给目标发**纠正**（停止当前轮后，
把纠正当作一条新的用户消息重新输入）。

老部署没有目标服务时，回落到「包成一条用户消息投进去 + 等那一轮结束」：能派、能等，
但没有 `none`（后台监视要读目标状态），调用会直接说明这一点。

### 按需汇报：`report_task`

`dispatch_task` 的 `progress` 是廉价的被动过程稿；当 A 怀疑方向偏了，或者准备纠正/验收时，
可以调用 `report_task`，让目标会话的**只读汇报助手**回答具体问题：

它只用于**审阅下属的执行进度**，不是向专家请教：专家/顾问不是下属，有问题请用 `consult_task`。

| 参数 | 说明 |
|---|---|
| `targets` | 要汇报的目标，最多 8 个；每个目标一次独立模型请求，逐目标并行 |
| `ask` | 汇报要求：要它回答什么、引用什么证据、怎么区分事实/自述/推断/未知 |

它读取目标 `session.deriveMessages()` 里的模型可见历史，追加当前 goal objective 和 `ask`，
发一次独立请求。**只读**：不打断目标、不创建 goal、不改 `pending` / `reviews`、不给目标
注入消息；也不依赖任何外部旁注插件或命令。

返回 `{ status, results, note }`，每个结果包含：

```text
{ target, status, report, goalPhase, asOf, truncated, note }
```

单个目标最多等 300 秒（5 分钟）；超时或失败只影响它自己，其他目标照常返回。
报告会明确区分「有证据的事实 / 目标的自述 / 推断 / 未知」。

限制：

- 只读**模型可见历史**：历史窗口外、没有落进历史的工具输出看不到；
- 汇报是另一个模型的总结，不是真相；关键结论仍要 A 自己看证据；
- 它不改变派单状态，不能代替 `dispatch_task` 取结果，也不能代替 `reviews` 审核。

### 咨询：`consult_task`

如果 A 不是要派活，而是有一个具体问题需要目标专家回答 —— 尤其希望它**实际查文件、
跑命令**再回答 —— 用 `consult_task`。它把问题作为一条真实用户消息投递进目标会话，
目标用自己的完整工具核实后回答，回答作为工具结果返回给 A。

咨询对象要有明确依据：目标标题含「专家」「顾问」等字样，**或**连接线描述里明确写了
可以咨询；两者都没有时不要咨询。工具描述里会列出每条连接线的标题与描述，供模型判断。

| 参数 | 说明 |
|---|---|
| `targets` | 要咨询的目标，最多 8 个；多目标并行，每个目标独立一轮 |
| `question` | 问题正文。写清要它回答什么、看哪些文件/模块、给什么证据 |

与 `report_task` 的区别：

| | `report_task` | `consult_task` |
|---|---|---|
| 是否投递进目标会话 | 否（旁注请求） | 是（普通用户消息） |
| 目标能否读文件/跑命令 | 否 | 是（完整工具，必要时可修改文件） |
| 界面是否可见 | 否 | 是（目标会话里出现问答） |
| 是否改变目标状态 | 否 | 只产生一轮普通对话；不建 goal、不写 `pending` / `reviews` |
| 适用 | 审阅目标已有的历史 | 向专家问一个新问题、要它动手核实 |

行为边界：

- **忙就跳过**：目标正在跑一个回合时，本次咨询跳过（结果里标 `busy`），不排队、不打断；
  多目标时只跳过忙的那些，其余照常问；
- **不建 goal、不审核**：咨询不是交付，回答完这一轮就停；
- **允许目标修改文件**（用户明确选择）：包装里要求它说明「改了哪个文件、为什么改」；
  这只是提示词约束，真正的工具集仍由目标会话自己决定；
- 单目标超时 10 分钟；超时/用户停止/取消时，已收到的文本进 `progress`，不冒充回答；
- 咨询内容与回答会留在目标会话历史里，之后目标仍然记得这次问答。

返回 `{ status, results, note }`，每个结果包含 `{ target, status, reply, progress, note }`。
`status` 为 `ok` 时 `reply` 才是完整回答；`busy` / `timeout` / `interrupted` / `cancelled` /
`error` 都不是。

### 停止与唤醒：`control_task`

`dispatch_task` 负责把活交出去；`control_task` 负责在任务跑到一半时**停住**，以及把
停住的目标**唤醒**。它只做控制，不派新任务、也不取结果。

| 参数 | 说明 |
|---|---|
| `action` | `stop` = 停止目标当前任务并暂停；`resume` = 唤醒暂停的原目标继续 |
| `targets` | 要控制的目标，最多 8 个；每项可用序号、完整标题、标题片段或会话 id |

**stop**：

- 与目标窗格的停止按钮同一个底层动作：`agent.cancel({ kind: 'hook' })` 中止当前回合，
  `keepInbox: true` 保留目标队列里用户自己的输入；
- 顺序是 `disarm → cancel → 等 agent 真正 idle → pause`。**不能先 pause**：
  `goal-round-driver` 看到暂停且 agent 还在跑，会补一刀 `aborted.user`，A 会把这次停止
  误读成「用户接管了这一单」；
- 停止成功返回 `status: "paused"`，这单按「未交付」结清；目标不会再自动开新轮；
- 最多等 30 秒。超时返回 `status: "stopping"`，**不是 paused**：目标已经不会自动推进，
  但当前回合还没确认收尾；这单保留在后台，稍后再 stop 一次确认，或用 `dispatch_task`
  取结果。不要拿 `stopping` 当「已停止」；
- 停止晚了一步、目标已经完成时返回 `complete`，这单留给 `dispatch_task` 取结果；
- 只停本会话派出去的任务（`pending` 里有票，或 goal 带 `[任务分派]` 前缀）；不会杀后台
  进程或目标自己派出的子代理。

**resume**：

- 走 `goals.resume` 恢复**原来的 goal**，不重发任务正文、不新建目标；目标从原 objective
  继续，历史还在；
- 成功后重新开一张派单票，之后用 `dispatch_task`（不带 `task`）等结果；
- 拒绝：`complete`（先取结果并审核）、`blocked`（策略性停住）、用户手动停止的目标
  （先问用户）、不是任务分派创建的目标、还在停止收尾（agent 仍 running）的目标。

状态词：`paused` / `stopping` / `resumed` / `running` / `complete` / `blocked` / `failed`。
`deliverable` 恒为 false —— 控制不是交付。

### 交付之后：不审核，不能再派

每单真正交付（`deliverable: true`）之后，这个目标进入「待审核」。不记录审核结论，
下一次给**同一个目标**派新任务会被直接拒绝；其他目标不受影响 —— 按目标拦截，不是全局。

审核是独立的一次调用，参数是 `reviews`（数组）：

| 字段 | 说明 |
|---|---|
| `target` | 要审核的目标：序号、标题片段或会话 id |
| `verdict` | `accepted`（验收通过）或 `rejected`（驳回） |
| `note` | 审核依据；**驳回时必填**，写清缺哪条证据、期望看到什么 |

- `accepted`：清掉待审核状态，之后可以给这个目标派新任务。那个已完成的 goal 也会被清掉，
  目标条上的「待审核」随之消失。
- `rejected`：同样清掉待审核状态和已完成的 goal，之后用 `dispatch_task` 带 `task` 把具体缺口
  发回去（对方正在跑时就是纠正）。不写 `note` 会被拒绝 ——「再做一遍」这种空话没有意义。
- 审核与派单**必须分开调用**：带 `reviews` 时再带 `task` 会被拒绝。
- 只有 `complete`（真正交付）才需要审核；`failed` / `blocked` / `paused` / `interrupted`
  算「没交付」，不挡下一单。
- 待审核状态会落盘（`~/.dsh/storages/pane_dispatch_reviews.json`）：Host 重启后这条账仍然有效，
  未审核照样拦。上一单的结论留在目标会话的历史里，重启后可以回去复核；撤掉箭头会清掉记录。
- **审核的最终真相是目标上的 complete goal，而不只是那张审核账**。后台监视在目标进入
  complete 时就落账，不再等结果被取走；即使审核账因为「交付后还没落盘就被重启」而丢失，
  `reviews` 也会从 complete goal 补账。新派单在 `goals.create` 之前也会看一眼目标：
  是本插件派的、且已经 complete，就拒绝覆盖并提示先审核，绝不会把待审核的 goal 悄悄换掉。

### 目标条上的「审核完成」

`complete` 的 goal 不再被 GoalBar 隐藏，而是显示为「待审核的目标」，右侧有一个对勾图标
（tooltip「审核完成」）。点击走现有的 `goals.clear`，goal 这时才真正消失。它对
**用户创建的 goal** 和**委派产生的 goal** 一视同仁。

- 模型 `reviews` 通过/驳回时，也会顺手清掉那个 `complete` goal —— 目标条同步消失。
- 人先点了「审核完成」时，goal 已经被清掉；插件下次派单会以 goal 为准，把待审核记录
  一并放行，不会再拦。
- 这条 UI 来自核心补丁 `patches/dsh-goal-awaiting-review`：升级 DSH 后跑一次
  `./apply-dsh-patches.sh`，并刷新浏览器。Host 不需要重启。
- 刷新/重启后不会「又看不见」：`complete` 的 goal 写在会话事件日志里，重启后投影重放；
  待审核记录也落盘。如果重启前结论还没被取走，`adoptOrphanGoals` 会给完整的 goal
  补一条待审核记录，保证目标条和派单闸一致。
- 边界：用 `/goal` 或 `goals.create` 新建目标会**替换**掉 `complete` 的旧 goal，等于跳过审核。
  这是 goal 领域现有语义，本插件不改。

### 派不出去的时候，错误会说到点子上

真机联调时踩过两次「错误信息把人带偏」，所以这里的措辞是特意分层的：

| 症状 | 说明什么 | 该做什么 |
|---|---|---|
| `Host 一次都还没收到过界面的绑定同步` | 界面那半边没接上（页面没刷新、远端命名空间没挂） | 刷新页面，确认顶部有 `平铺 \| 设计` |
| `以这个会话（<id>）为起点的箭头一条都没有` + 列出**现有关系** | 同步是通的，但箭头不属于这个会话 | 核对「发起调用的会话」是不是箭头**起点**那张卡片 |

第二条会按 `「派出方」→「目标」` 的正确方向把现有关系全列出来 —— 第一版把目标名当成了
派出方报出去，用户照着它查只会越查越远。

### 边界与取舍

- **一次可以派给多个目标，这些目标同时开工**。`targets` 给几个，就有几个目标在同一批里
  并行推进，每个目标一条独立的等待，结论按请求顺序列在 `results` 里。可派目标多于一个
  时必须显式指明 —— 不会替你猜「是不是要全部派一遍」。
- **有箭头就优先派，派完一批还会报空闲目标**。工具说明把「优先分配」写成默认策略：目标空闲、
  活能拆成独立块时，尽量把多个目标一次列进 `targets` 并行开工，而不是一次只派一个、等回来再派。
  主会话看不到谁空闲（工具描述刻意不写忙闲，避免每轮失效提示词缓存），所以每次派单/收单的结果
  `note` 会附上「其余空闲目标」名单 —— 排除本批已派、正在跑、以及还有结论没取的目标；
  主会话在同一回合就能决定继续派，而不是只派一个就收工。
- **交付之后先审核，才能派下一单**。真正交付（`deliverable: true`）的目标进入「待审核」，
  未记录审核结论就再派会被拒绝；按目标拦截，不影响其他空闲目标。审核通过/驳回都会清掉
  待审核，驳回必须写 `note` 说清缺口。`failed` / `blocked` / `interrupted` 不算交付，不需要审核。
  这份状态会落盘（`storages/pane_dispatch_reviews.json`），Host 重启后仍然有效；撤箭头会清掉。
- **`wait` 决定这一批什么时候返回**。`all`（默认）等这一批**全部**有交付结论；`any` 第一个
  有交付结论就返回，其余标成 `running`、留在下一次续等；`none` **不等** —— 给了 `task`
  且目标空闲就是「派完就走」（立刻返回 `dispatched`），给了 `task` 且目标正在跑就是
  「停当前轮后重新提交纠正」（返回 `redirected`），没给 `task` 就是「只看一眼状态」，都不阻塞。
  `any` 只是「更早看到第一个结果」，**不会**让整批更快拿全 —— 反而要多调几次，每次都得
  重发一遍工具描述。
- **派完就走之后一定会被拉回来收尾**。派出去的任务不会自己消失：只要还有没取结果的，
  A 结束回合前会收到一次提醒（`agent/turn-stopping` 里 `inject()` 一条独立来源的消息，
  让这个回合继续走一步），提醒它回来把结论收掉。所以「先做自己的事」不会变成「忘了收」。
  同一回合只提醒一次，取完就不再提醒。
- **每 5 分钟报一次过程稿，不设总超时**。工具调用最多等 5 分钟：这一批有交付结论就直接回；
  没做完就带着**当前过程稿**返回（`status: running`、`deliverable: false`），派单方再调一次
  （省略 `task` 与 `targets`）接着等。这样长任务不会被误判失败，派单方每 5 分钟能看到一次
  进展。续等不查「对方忙不忙」—— 它当然在忙，那正是你在等的事。
- **目标正在跑时给 `task` 是「纠正」，不是第二个任务**。纠正会先挂起目标的自动推进，
  再停止它的当前轮（与界面停止按钮同一个底层动作：abort 当前回合、保留排队输入），
  然后把纠正作为一条**普通用户消息**重新提交，最后 `resume` 目标 —— 如果停止把它暂停了，
  这一步会一并启动；不新建目标；返回 `status: redirected`。A 看到过程稿发现方向不对时
  可以马上改，不必等目标按错的方向跑完再重派。停止原因记成 `hook` 而不是 `user`：
  `aborted.user` 的语义是「用户接管了这一单」，插件不能冒充用户，否则 A 自己的后台监视
  会把这次纠正误读成用户抢单。一次调用里不能把「纠正正在跑的目标」和「给空闲目标派
  新任务」混在一起 —— 同一个 `task` 会有两种语义，必须分开调用。
- **用户手动停止目标时，A 收到的是 `interrupted`，不是 `paused` 或 `running`**。用户在界面上
  按停止会产生 `turn/end` 的 `aborted.user`，插件据此立刻收口：`interruptedBy: "user"`，
  `deliverable: false`，过程稿单独放 `progress`。A 可以继续做不依赖这个目标的部分；但**不能
  越过用户去纠正它** —— 用户接管了这单，等处理完再派。这同时覆盖两种情况：用户停的是 goal
  轮（goal 变 `paused`）和普通轮（goal 仍 `active` 但自动推进被 disarm）。
- **对方「受阻 / 暂停」之后仍然可以再派**。`goals.create` 只允许替换 `complete` 的旧目标，
  其他阶段必须先清掉 —— 所以派单时会先看一眼：旧目标是 `blocked` 或 `paused`，就清掉它
  再建新的，并在结果里说明「派单前已清除对方一个受阻的旧目标（原因：…）」。清除会保留
  墓碑与历史，不是抹掉记录。`active` 的旧目标**不**会动，那是真在干活。
- **交付要求写在任务包装里，验收由 A 复核**。对方被要求把「怎么算做完」拆成可检验的检查项、
  每条给出证据，缺少证据时不许宣布完成；A 拿到结论后必须对照验收标准复核，不达标就带着
  **具体缺口**重派，而不是笼统地「再来一遍」。注意这只是提示词层面的约束 —— 完成与否仍由
  对方自评，真要根治得把验收权从执行者手里拿走。
- **有结果没领取时不会被新派单覆盖**。这时会明确回答「上一次的结果还没取」，让任何一方
  先把结论收走再派新的 —— 结论只会交付一次，覆盖掉就真没了。用户手停产生的 `interrupted`
  也算一种待领取结果：A 带 `task` 来纠正会被拒，先取走中断说明；之后按用户指示重派。
- **批量派单先全部预检再动手**。有一个目标在忙，整批一个都不派 —— 否则会出现「派出去
  一半」，模型拿着半截状态还得自己猜哪些生效了。预检之后仍可能有目标在建目标那步失败，
  那种情况如实记成 `failed`，其余照常跑完，整批状态是 `partial`。
- **箭头不跨刷新保存**。与布局一样，刷新页面就重置；Host 侧的绑定会在页面重新挂载时
  被对齐成「页面上的箭头」的样子（所以刷新后不会留下看不见的授权）。删掉一条箭头等于
  撤回授权，正在等那个目标的记录也会一起作废。
- **Host 重启后，派出去的单子还能认回来**。`pending` 只活在内存里，而 goal 在 DSH 的
  目标服务里、重启不丢 —— 两者一脱节，A 再来续等就会被当成「从没派过」，活干完了结论却
  永远拿不到。所以续等之前先凭 goal 的固定前缀 `[任务分派]` 把单子认回来：还在跑的接着
  盯，已经做完的如实说「结论没能自动恢复，去那个会话里看」。
  这也意味着**不另存一份 `pending`**：重启后以 goal 为真相现场反查，落盘文件坏了也不影响。
  代价是重启前已做完、结论只剩在会话历史里的那种，结论文字恢复不了，只能给指路。
- **重启后不能把「goal 还 active」当成「还在跑」**。DSH 重启只把进程内的 `activation`
  置成 `disarmed`，durable `phase` 仍然是 `active`；目标轮驱动不会自己恢复推进，会话也
  已经 idle。界面上的「已暂停的目标」就是 `active + disarmed`。所以状态必须由
  `phase + activation + agent.status` 合成：`active + disarmed + idle` 立即判成
  `paused`（说明 Host 重启后已停止），只有 `active + armed` 或 agent 真在跑才算
  `running`。否则 A 会看到永远不会结束的 `running`，而目标其实早停了。

### 任务分派踩过的坑

这几条都不是架构问题，是边界问题 —— 其中两条当时测试是**绿**的，因为测试替身跟着代码
一起写错了。

| 坑 | 症状 | 根因 |
|---|---|---|
| 卡住原因显示成错误码 | 用户看到 `round-limit`，而不是「连续三轮卡在权限上」 | `blockedReason` 的真实形状是 `{ code, message }`，代码却读 `explanation`，取到 `undefined` 后退回 code。测试替身照抄了这个错字段，所以一直没暴露 |
| 老部署上 `wait: none` 假装派成 | 返回 `dispatched`，实际一条消息都没投出去 | 后台监视依赖目标服务；没有它时那条分支什么都不做，却照样回成功 |
| 阻塞续等把结论吞成空串 | 任务做完了，A 拿到空结论，而且拿不到第二次 | 后台监视从派出那一刻就在听，阻塞等待只从「现在」开始听；两者同时结算时取了后者（可能是空的），还顺手把前者掐掉了 |
| 会话重连后再也读不到状态 | 明明做完了，要等满 24 小时兜底才记成 `unknown` | `goals.get()` 校验 agent 是不是活的；闭包里那个引用在重连后失效，每次读都抛错，被当成「读不到，继续等」 |
| 目标受阻后再也派不进去 | B 一旦 `blocked`，A 长期无法再派 | `goals.create` 只允许替换 `complete` 的旧目标，`blocked`/`paused` 必须先 clear |
| 结论与终态被切在两个窗口 | 后台攒到了结论却交不出去 | 后台监视一度按「5 分钟一段」反复退订重订：结论在某段说完、终态在下一段才看见。改成单订阅长听后消失 |
| Host 重启后结果成了孤儿 | 活干完了，A 回来收却报「从没派过」；收尾提醒同样数的是空表，所以也不响 | `pending` 只在内存里，重启清零，而目标会话的 goal 还在跑。两边脱节后谁也不认识这单。修法是不落盘、改为按 goal 的 `[任务分派]` 前缀现场认回来 —— goal 才是真相 |
| 新增箭头后主会话不认识新目标 | 必须 Ctrl+R 刷新页面，模型才说得出新目标 | 作用域工具的 `description` 在注册那一刻被算成了字符串；DSH 每次组装提示词都会重新读 `definition.description`，改成 getter 后绑定表一变就自动反映到下一次 step |
| 重启后 A 一直看到 `running` | 目标早停了、界面显示「已暂停」，`dispatch_task` 却永远说 `running` | 只读 `goal.phase`；重启只把 `activation` 置成 `disarmed`，`phase` 仍是 `active`。改成 `phase + activation + agent.status` 合成后才判成 `paused` |
| 审核账丢失后仍能派新单 | 界面显示「待审核」、`reviews` 却说没有，A 据此派了新任务 | 审核闸只认 `reviews`；交付时没落账、重启后 `pending` 也没了。改为 complete goal 作为最终真相：交付即落账、`reviews` 从 goal 补账、`createGoal` 前先看 goal |

共同规律：**同一个事实存了两份，却没写清谁是权威**。修完后的原则是 —— 后台监视以派出
时刻为起点，视野永远更长，它是权威；阻塞等待只是「这一次调用看到的那一眼」。重启认领
沿用同一条原则：`pending` 是缓存，**goal 才是权威**。

## 行为细节

### 派单光效

`dispatch_task` 真正开始投递时，平铺面板会播放一段青金色光效：

- 主窗格边框先亮一下；
- 一颗小而亮的流星（7px 白心 + 120px 金色柔光 + 96px 双层尾迹）从源窗格中心
  **直线**飞向目标窗格内的随机落点（四周留 20% 边距）；**不画轨迹线**；
- 多个目标**串行发射**：上一颗到达后，下一颗才出现；单程约 2.4 秒；
- 源/目标窗格边框高亮更强（3px 描边 + 56px 外发光）；高亮框是独立的覆盖层，
  不依赖窗格自身的边框/阴影，所以不会被选中态或裁剪吃掉；
- 光点到达目标时，目标窗格**同时**发生三件事：边框亮、**整体抖动一下**、
  **盖一层半透明白光**并在约 1.2 秒内慢慢消失，像被一颗小炮弹击中；
- 目标窗格没铺开：光点从主窗格飞向棋盘最近的边缘；
- 主窗格没铺开：光点从棋盘边缘飞入目标窗格；
- 主/目标都没有对应窗格：不播放；
- 整个平铺面板没显示（切到别的面板或页面）：完全不播放；
- 系统开启「减少动态效果」时跳过光点，只保留边框脉冲。

事件由 Host 的 `paneDispatch.pullVisual` 提供：只在内存里保留最近 64 条，不落盘、
不进模型。客户端每 300ms 取一次增量；首次挂载只记水位，不会重播历史派单。
它只影响视觉，不改变投递、等待和审核。


- 第一次打开棋盘会播种：当前会话所在的工作区排第一，再补一个别的，于是打开就是两个
  窗格并排，而不是一块空白。
- 窗格如何决定显示哪个会话：
  - **跟随型**窗格（`添加工作区` 铺开的）跟随该工作区最近更新的**真实对话**；
  - 一旦手动选了会话（或新建了会话），该窗格就钉在这个会话上；
  - **分屏新开的**窗格先空着，提示「为这个窗格选择会话，或新建会话」——
    这样两个窗格不会莫名其妙地显示同一段对话。它显示哪个工作区，是分屏菜单第二步
    选出来的。
- **普通空白会话不进会话菜单**：建了会话但一条消息都没发过的（Host 里 `blank: true`）
  不会出现在 `切换会话` 菜单里，也不会被跟随型窗格选为「最新会话」—— 否则误点几次
  「新建会话」就会堆出一长串同名「新会话」。这与 DSH 原生侧边栏「空白会话只显示当前
  选中的那一个」是同一个思路。**任务分派左侧是例外**：它把空白会话显示成「未命名会话」
  卡片，方便建完立刻连线；每个工作区只显示最近更新的一条，历史空壳不会刷屏。
- **带目标记录的空会话**：在任务分派左侧显示为「未命名员工」，因为「先建目标、连成目标、
  再让上级往里派活」正是真实用法；平铺 `切换会话` 菜单和替换菜单里仍然按目标处理。
  目标开始对话或被派单后，显示真实标题（不再叫未命名员工），也没有额外徽标。
  目标记录由 Host 独立落盘（`storages/pane_dispatch_targets.json`），**创建即存在**，
  不依赖「保存画布」；画布保存只负责节点、边和位置。空目标不会出现在平台原生会话
  列表里（平台只显示当前选中的空白会话），所以任务分派左侧每张卡片右上角都有垃圾桶：
  普通会话、空白会话、员工目标统一走平台删除确认框；删除目标时会同时清掉目标记录和边。
- **`新建会话` 优先复用普通空白会话**：本工作区里已经有普通空白会话、且它没被别的
  窗格钉住时，直接切过去（仍应用该窗格暂存的模式），不再让 Host 新建一条空记录。
  任务分派工作区行上的 `创建会话` 图标遵循同一条复用规则，只是**不切换任何窗格**，
  新卡片只出现在左侧列表里。目标不参与复用 —— 被切走会让任务分派里的节点悄悄换了会话。
- **分屏菜单第二步的候选**：列出**全部**工作区，但还没铺开的排在前面（分屏的第一
  意图就是再摊开一个工作区），已经铺在别的窗格里的排在后面并把右边提示换成
  `已打开`（其余显示路径）。保留已铺开的工作区是有意的：同一个工作区开两格看两个
  会话是合理用法，而且所有工作区都铺开之后，分屏仍然有别的工作区可选。
  `返回` 那一行右边会显示当前选中的方向，因此第二步里也看得见这次是往哪边切。
- **`替换工作区` 的候选是全部工作区**（模型里的 `workspaceCandidates`：侧边栏顺序 +
  `open` 标记），与顶部 `添加工作区` 的 `unopenedWorkspaces`（只列未铺开的）**不再共用**：
  替换要支持「同一个工作区换一个会话」，所以已经铺开的也必须出现；添加是往棋盘上加一个
  新工作区，已经铺开的没有必要再加一次。第一级一个工作区都没有时仍然显示「还没有工作区」。
  选中工作区后进入第二级：第一条固定是「新建会话」，然后是它已有的会话；选会话走
  `replaceWorkspaceWithSession`，工作区与会话在同一次 publish 里换完，不会闪一下
  新工作区的最新会话。真要对调两格位置仍用拖动标题栏那条路，它不重开对话。
- **第二步的 `新建工作区…`**：一个工作区都没注册过时它照样在，于是棋盘仍能长出第一格。
  点它会打开文件夹选择器，选中的目录注册成工作区后直接切进新窗格；用户取消就什么都不做，
  选择器本身打不开时窗格上会写明是「无法打开文件夹选择器」，而不是含糊的添加失败。
  方向在关菜单之前就抓进了局部变量 —— 关菜单会把 `splitDirection` 复位，等到选择器
  回来时已经读不到了。
- 分屏菜单是**受控**弹出菜单（`Popover` 的 `open` + `onOpenChange`）：只有它能被外部
  复位。点方向、选工作区、点别处、按 Esc —— 任何一种关闭都会把菜单复位回第一步，
  否则下次打开会停在上次选的方向上。离线测试对「选完工作区后」与「点别处关闭后」
  两条路径各有一条断言。
- 每个窗格各自持有 `ctx.sessions.retain(..., { source: 'splitWorkspaces' })` 引用，
  所以侧边栏的主选择不受影响，多个会话可以同时开着。
- **拖动交换位置不会重开会话**：交换的是布局树里两个叶子的 key，窗格记录（工作区、会话引用、
  预选模式）一个字段都不动，于是两个窗格的 `useSessionReference` 效果一次都不重跑 ——
  引用不松手，对话的历史与本地状态就整段留着。这条路只在**同一层**分屏里成立
  （React 只在兄弟节点之间按 key 搬动），跨层交换仍然会重建那两棵子树，见坑 6。
- 窗格列表与布局树保存在插件里（不是 React 状态），因此切回 Conversation 面板再切回来
  不会丢；刷新页面才重置。
- 模式选择是「按窗格」的：会话还是空白时选择立刻生效（`remote.agentPresets.select`）；
  会话已经跑过回合时 Host 会拒绝改标签，此时选择被暂存，菜单里标注 `下一个会话`，
  等该窗格下一次新建会话时应用。被拒绝的原因会显示在窗格上，且不会影响会话创建。
- MCP 开关是「按工作区」的（与上一条正相反）：选择存在**工作区路径**上，关掉再开的窗格
  读到的还是同一份；改动立刻作用于该工作区的**所有会话**（含已经跑过回合的），不需要
  新开会话。宿主服务由 `@local/dsh-mcp-workspace-policy` 提供（含按 cwd 施加
  `tools.restrict` 的策略与落盘），本插件只是它的界面。
- 没挂预设注册表的部署会得到 `gateway/invocation-unavailable`，此时棋盘照常工作，
  只是不显示模式选择器。
- `添加工作区` 不会顺手创建会话，也不会把主面板切走。
- **焦点键的作用范围是「这个面板在屏幕上」，不是「焦点在窗格里」**：监听挂在文档的捕获
  阶段，面板没显示时（棋盘根节点的标记不在）什么都不做，因此点过棋盘空白、刚用侧边栏图标
  切过来这类「焦点落在 `body` / 侧边栏」的情形照样管用 —— 这一条是用户实测报回来的，
  见下面的坑 4。浮层（菜单 / 对话框）盖着时、焦点在棋盘之外的输入框里时一律放行：
  那些键是别人的（「设置 → 快捷键」的按键录制就在浮层里）。
  切过去之后键盘光标会跟着进目标窗格的输入框；目标窗格还没有会话、没有可编辑的输入框时
  只切高亮，**不把光标从原来那个窗格里抢走**。
- **鼠标点亮窗格时的光标归属**：送光标挂在 `click` 上（**不是** `pointerdown`），并且**放弃**
  两类落点 —— 落点是控件（按钮 / 链接 / 菜单项 / 输入框 / 可编辑区），以及用户刚拖选出
  一段文字（选区不是折叠的）。前者是为了不打断「用户正在操作那个控件」，后者是因为
  `focus()` 会实测把那段选区整段抹掉。两条都是真浏览器量出来的，见坑 5。
  `Tab` 进窗格只切高亮、不搬光标：Tab 的落点是浏览器的地盘，标题栏按钮与会话区里别的
  可聚焦元素都要能 Tab 得到。

## 踩过的六个坑（改这块代码前先读）

1. **焦点用错了颜色 token。** `--dsw-alias-brand-primary` 在深色主题里是**近白**的中性
   填充色（`--dsw-static-neutral-bluish-50`），拿它当焦点标题栏的底色再配白字会得到
   白底白字。蓝色强调色是 `--dsw-alias-brand-primary-new-colorprimary-new-color`
   （浅色 #4176e6 / 深色 #5686fe），兜底用静态的 `--dsw-static-deepseek-500`，
   **不要**把它兜底到那支中性填充色。离线测试里有两条断言守住这件事。
   另外白字直接压纯强调色只有 3.3:1，所以渐变两端要跟黑混一下把蓝压深。

2. **标题栏里的可选孩子必须带 key。** React 对没有 key 的兄弟节点是按位置匹配的：
   焦点标记、模式选择器这类「有时有、有时没有」的孩子一旦出现/消失，位置就会错开，
   React 会把用户刚按下鼠标的那个按钮**复用**成别的控件，`click` 于是落到错误的处理
   函数上。真实症状是「点『向下分屏』却变成向右分屏」。现在标题栏、错误行、对话本体
   都带固定 key，离线测试会检查「key 齐全且唯一」「焦点切换前后标题栏结构完全一致」。

3. **焦点键为什么是 Alt，以及为什么必须挂捕获阶段。** 这组键要在输入框里也能用，
   而 Chromium 的 contenteditable 已经把常用的方向键组合占满了：
   `Shift+←/→` 逐字选字、`Shift+↑/↓` 按行选字、`Ctrl+←/→` 按词跳光标、
   `Ctrl+↑/↓` 跳段首段尾、`Ctrl+Shift+←/→` 按词选字。所以 Shift 或 Ctrl 单独配方向键
   都会废掉输入框里的一个高频操作。`Ctrl+Alt+方向键` 看着像个出口，实际上被桌面环境
   拿走了（GNOME/Unity 的 `switch-to-workspace-{left,right,up,down}` 就是
   `Ctrl+Alt+方向键`，在窗口管理器那一层就被吃掉，页面根本收不到）。
   **只有 `Alt+方向键` 在输入框里没有任何原生含义、桌面也不占**，代价最小；
   它唯一的牵扯是浏览器里 `Alt+←/→` 的前进后退 —— 所以处理必须挂在**捕获阶段**并
   `preventDefault()`（同时 `stopPropagation()`，免得输入框再把它当光标操作处理一遍）。
   `AltGraph`（某些布局上等于 Ctrl+Alt）与输入法组字中一律放行，绝不抢输入法的键。

4. **键盘处理不能挂在棋盘节点上。** 第一版把它挂在棋盘根节点的 `onKeyDownCapture` 上，
   理由是「捕获阶段才能在输入框之前拿到事件」—— 这条没错，但它还藏了一个错假设：
   事件目标一定在棋盘里。实际点过棋盘空白之后焦点会落到 `document.body`，刚用侧边栏
   图标切过来时焦点还在侧边栏按钮上；这两种情况下事件都不流经棋盘节点（合成事件只沿
   目标的祖先链派发），按键全都没反应 —— 用户看到的现象就是「只有焦点在输入框里时
   `Alt+方向键` 才有效」。现在监听挂在 `document` 的捕获阶段（仍然早于输入框），
   并用棋盘根节点的标记判断面板在不在屏幕上：主面板是按 key 渲染的，切到别的面板时
   棋盘会卸载、标记随之消失，处理自然失效，不需要额外记账。

5. **「点亮窗格就送光标」有两处只有真浏览器才答得上来的行为。** 离线测试的假 `document`
   模拟不了浏览器的**默认动作**，这三条都是拿无头 Chrome + CDP **可信鼠标输入**量出来的
   （`node tools/browser-probe.mjs` 会把前两条逐条再跑一遍，不需要 DSH 服务）：
   - **不能挂在 `pointerdown` 上**：单击一个不可聚焦的元素（消息段落就是）时，`mousedown`
     的默认动作会把当前焦点抹成 `body` —— 在 `pointerdown` 里 `focus()` 出来的光标紧接着
     就被这一步擦掉。挂到 `click` 上才留得住（`click` 之后没有会改焦点的默认动作）。
   - **不能无条件聚焦**：在 `click` 里对一个 contenteditable 调 `focus()`，会把刚拖出来的
     选区**整段抹掉**（实测：选区从 `ectable text here` 直接变成空、折叠）。这等于把
     「选中消息复制」废掉，所以只要选区不是折叠的就一个字都不碰。单击时先到的那次
     `mousedown` 已经把旧选区清掉，因此不会因为页面上某处留着陈年选区而永久失灵。
   - **关窗格要等一帧**：顶替焦点的窗格原来嵌在被折叠掉的那层分屏里，布局树塌陷后 React
     按 key 找不到原来那棵子树，只能重建 —— 立刻 `focus()` 只会聚焦到一个马上要被丢掉的
     旧输入框，重排一结束光标就没了。等一帧（`requestAnimationFrame`，没有它的环境退回
     `setTimeout`）再聚焦，才落在真实存在、且会继续存在的那个输入框上。

6. **交换两个窗格的位置只能靠「换 key」，而且 React 只在兄弟节点之间搬动。**
   同一个效果有过三种写法，只有第三种是对的：
   - **换两个窗格记录里的工作区 / 会话**：两边 `useSessionReference` 的效果都会重跑，而 DSH 的
     会话引用契约是「最后一次释放就拆掉会话的本地作用域与历史」—— 两个对话都会白重开一遍。
   - **把布局树里的叶子整棵换过去**：结构共享失效、整条路径重建，React 按 key 找不到原来的
     子树，只能卸载重建，同样白重开。
   - **只把布局树里两个叶子的 `key` 互换**（模型里的 `swapLeaves`，存储层 `swapPanes`）：
     分屏的层级与比例、窗格记录一个字段都不动。于是在 React 眼里这仅仅是「同一层里的两个
     兄弟换了 key」，它会**整体搬动那两棵子树**，会话引用一次都不松手。

   第三种还依赖一个前提：**叶子窗格必须是分屏 div 的直接孩子**。原来每个孩子外面还套着一层
   占位 div（比例写在它身上），而 React 的 key 匹配只发生在同一个父节点下 —— 隔着一层就配不上，
   交换会悄悄退化成重建。现在比例写在窗格自己的 `flexGrow` 上，占位 div 只留给子树。

   **跨层交换（两方不在同一层分屏里）仍然是重建。** `A | (B/C)` 里把 A 和 C 换位置，React 没法把
   一棵子树搬到另一个父节点下，只能卸载重建；实测那一格会闪一下「正在打开会话…」
   （本地小会话下无头 Chrome 多次量到 50~245ms，三五帧到十几帧），格内的滚动位置与展开后的
   工具输出也会重置。同层交换（任意两个同层或相邻的窗格）完全没有这些代价 —— 这是
   「拖动交换位置」敢做的前提，真浏览器探针把这两件事分别量一遍并如实报告：
   `node tools/swap-probe.mjs`。
   若哪天想让跨层交换也免掉这一下，得改**会话引用的生命周期**（同一个会话的引用在多个窗格间
   共享，最后一次释放延后一个任务执行，让同一次重排里的卸载 + 重挂抵消掉），而重建本身带来的
   滚动与展开状态丢失仍然免不掉 —— 代价不小、收益只有几十毫秒，暂时不做。

## 科幻主题（平铺模式）

平铺面板的外观在 `client.styles.js` 末尾，以追加覆盖的方式实现，不改 DOM/逻辑：

- 在 `.dshSplitWs_root` 内覆盖完整深色主题 token，让共享会话内容也切到深色；
  主界面其它区域不受影响。
- 面板头、窗格标题栏、视图标签、分隔条改成深色 HUD。活动窗格用橙色标题栏 +
  `NODE 01 / ACTIVE` 标识，不靠窗格外框（遵守既有的焦点契约）。
- 动效只有边框流光、活动标题栏、分隔条菱形呼吸、顶栏左右扫光；没有下滑扫描光栅。
- 模式/会话这类 portal 菜单仍跟随页面主题，不在这套 token 覆盖的作用域里。

## 每个会话的内容区配色

平铺面板会给每个窗格的内容区换一种深色底，用来一眼分清哪一格是哪段对话：

- **颜色跟会话走**：按会话 id 稳定映射；刷新、恢复布局、拖动交换窗格之后，同一段
  对话还是同一种颜色。还没选会话的空窗格按工作区 id 分色。
- **同一屏不重复**：首选色被别的窗格占了，就顺着色板往后找空位；八个窗格以内不会
  有重复，超过八个才开始复用（这时重复无法避免）。
- **只染内容区**：标题栏、视图标签、窗格边框保持原来的科幻主题外观，配色只是
  `.dshSplitWs_paneBody` 上的背景变量。想改回无色，删掉那条规则里的 tint 覆盖即可。
- **半透明渐变**：不是整块染成实心色，而是「左上角柔光 → 向下淡出」的两层半透明
  渐变（最高 20% 色相）；会话根保留 44% 的深色遮罩，气泡与输入框接近原来的深色，
  只带一点色相。这样像一块带色温的玻璃，而不是一块彩色纸。
- **文字可读**：色相只出现在背景渐变里，并同时提亮三级文字（`#6f8aa0` → `#839db2`）。
  每种颜色的最亮处上，正文 ≥ 10.6:1、次要文字 ≥ 6.2:1、三级文字 ≥ 4.6:1，都过
  WCAG AA。逐色断言在 `test/tint-contract.mjs`，改色板或混合比例时它会拦住把文字
  压暗的改动。

## 字体与消息浮现

- **平铺面板的标题、按钮、菜单**使用自带的**站酷快乐体**；**会话正文保持系统原字体**
  （主界面和平铺面板的对话都是），侧边栏、设置也不变。字体文件在 `fonts/`
  （SIL OFL 1.1，许可原文在 `fonts/OFL.txt`），由 Host 半边的
  `/split-workspaces-fonts` 前缀路由提供。如果系统没有安装站酷快乐体、或字体路由
  不可用，会依次回退到 `Noto Sans CJK SC` / `Noto Sans SC` / `PingFang SC` /
  `Microsoft YaHei` / 系统默认字体，不会出现方块字。
- 中文与全角标点用 710KB 的简体中文子集，拉丁字母 / 数字 / 半角标点用 5KB 的拉丁
  子集，通过 `unicode-range` 分工。代码块继续使用等宽字体，不受影响。
- **正文逐行浮现**：主界面和平铺面板的**助手正文**（`assistant-step` 且不是思考
  过程）按 Markdown 块（段落、列表项、标题、引用、代码块、表格）逐块淡入并上浮
  6px，每块 2 秒。同一段落内部的自动换行仍作为一块（浏览器排版结果，CSS 无法
  拆成视觉行）。用户消息、工具调用行、思考过程保持静态出现；流式输出追加 token
  时已有段落不会重播，新段落才浮现。
- 系统开启「减少动态效果」时，浮现动画自动关闭。

## 文件

源码按职责拆成几个文件（都远小于 800 行）。DSH 的浏览器模块系统支持**包内代码块**：
入口用 `require.async('./client.xxx.js')` 请求同目录文件，宿主按
`/plugins/<包名>/client.xxx.js?rev=<版本>` 提供，因此入口不必背着全部实现。

- `client.js` —— 入口：装载各代码块（样式 / 词典 / 模型 / 布局 / 模式 / MCP / 会话视图 / 菜单 / 窗格 / 视图）、
  注册插槽、注入样式，把 `Alt+方向键` 登记成框架的固定快捷键，并在文档上装上它的键盘处理；
  另外提供 `openWorkspaceDirectory(path)`（走 `remote.session.openWorkspacePath`）
  给窗格的「打开目录」按钮，以及 `requestSessionDelete(sessionId, displayTitle)` ——
  惰性解析 `dsh-session-delete` 的 `sessionDeleteUi` 服务，把「删除这一行」转交给它的确认弹窗，
  并在删成功后用 `paneStore.forgetSession` 松开所有钉着这个会话的窗格。
- `client.fx.js` —— 派单光效：主/目标窗格闪烁、贝塞尔光点与拖尾、多目标依次发射；
  窗格没铺开时用棋盘边缘取点，整块面板不在屏幕上时直接不播。
- `client.view.js` —— 棋盘层：`Splitter`（分隔条）、
  `SplitPanel`（按布局树渲染窗格与分隔条、面板顶部动作、棋盘根节点上的「在屏幕上」标记）、
  `installPaneKeys`（文档级的 `Alt+方向键` 处理，聚焦交给窗格块的 `focusPaneInput`）。
- `client.views.js` —— 每格自己的会话视图标签栏：从框架的 `conversation.view` 槽位读清单

  与 MCP 同构的那套（降级分支、乐观更新与回滚、按工作区写回），外加两条本块特有的
  产品决定 —— 技能库服务没挂上时标题栏**不出现**这个按钮、目录为空时弹层给出去处
  而不是一片空白；并断言每行都带得出技能描述。
- `test/open-contract.mjs` —— 「用文件管理器打开工作区目录」的离线契约测试
  （`node test/open-contract.mjs`）：`remote.session` 被换成记账的替身，因此断言的是
  插件**真正发出去的调用** —— 先问 `canOpenWorkspacePath`（只问一次），再把该窗格的
  路径按 `{ path }` 的形状交给 `openWorkspacePath`；以及五种失败（没有会话服务、
  没有图形环境、路径验不过、打开命令失败、连接断了）各自说出什么话。

- `test/delete-contract.mjs` —— 「切换会话」下拉里**逐行删除**的离线契约测试
  （`node test/delete-contract.mjs`）：每行一个删除按钮、两个按钮平级（不是按钮套按钮）、
  按钮的提示语带着**那一行**会话的名字、点一下就关菜单并把 `sessionId` / `displayTitle`
  交给 `sessionDeleteUi`（`ctx.get` 里放替身，因此走的是真实的惰性解析路径）、
  光点一下不动窗格状态、服务不在时窗格错误行明说「删除功能没准备好」、
  以及删成功后 `forgetSession` 把**所有**钉着它的窗格松开。
- `test/menu-contract.mjs` —— 标题栏弹出菜单的离线契约测试（`node test/menu-contract.mjs`）：
  菜单确实 portal 到 `document.body`、用 fixed 定位，窗格的 `overflow:hidden` 不再裁切它；
  宽度兜底值按视口收窄。
- `tools/browser-probe.mjs` —— **真浏览器**探针（需要本地装有 `google-chrome`）：用 CDP 可信
  鼠标输入把「光标归属」依赖的浏览器默认行为逐条量一遍，见坑 5。它不进离线测试
  （那些仍然零依赖），改这块代码前手动跑一次（`node tools/browser-probe.mjs`）。
- `tools/replace-probe.mjs` —— **真浏览器**探针：在**自己起的**另一个 `dsh web`（不碰你正开着的
  窗口）上把「替换工作区」点一遍，量几件离线测试答不上来的事：图标按钮真的点得开、
  第一级菜单真的列出全部工作区（当前这格标「已打开」）、点进第二级后第一条是「新建会话」、
  选中已有会话后那一格**还在原地**（矩形与 DOM 节点都没换，说明是「换了内容」而不是
  「关掉再开一格」），并留下打开菜单与替换之后的截图
  （`node tools/replace-probe.mjs`，约一分钟；可用 `DSH_REPLACE_PROBE_URL` 复用一个开着的服务）。
- `tools/rename-probe.mjs` —— **真浏览器**探针：验证「改卡片名称」。它用**临时
  `DSH_HOME`**（`sessions/` 是全新空目录，只有插件与工作区清单用软链接复制）起独立服务，
  因此不会改到你的任何会话。默认量的是**未命名规则**：新建的空白会话与未命名员工
  在左侧和画布上**都没有**铅笔（删除按钮仍在）。想顺带跑正向用例时，用
  `DSH_RENAME_PROBE_SESSION=<会话id>` 指定一个**已有标题**的会话，探针会把它**复制**进
  临时目录，在副本上改名并验证「左侧与画布都变、刷新后还在、空名字被拒绝、取消不改坏」
  （`node tools/rename-probe.mjs`，约一分钟）。
- `tools/swap-probe.mjs` —— **真浏览器**探针：自己起一个独立的 `dsh web`（不碰你正开着的
  窗口）与一个无头 Chrome，用**可信鼠标输入**真拖两次，量三件离线测试答不上来的事 ——
  指针跑到别的窗格上方时命中测试仍然准、交换换的是「位置」（矩形正好互换）、
  以及**子树是被搬动的还是被重建的**（拖动前给窗格和它的输入框打标记，交换后标记还在就是搬动；
  跨层交换会被如实报告为重建，见坑 6）。顺带把拖动途中的反馈截成 PNG 打印路径
  （`node tools/swap-probe.mjs`，约两分钟；可用 `DSH_SWAP_PROBE_URL` 复用一个已经开着的服务）。

## 本地开发

Profile 以 `link:` 指向本目录，`dsh-client-hmr` 会按 500ms 轮询**入口** `client.js`
（mtime / ctime / 大小），所以改入口就会在约一秒内自动重载浏览器插件，不需要构建。

注意：HMR 只盯着入口文件，而代码块 URL 带着「入口文件的 mtime / ctime / 大小派生的版本号」，
因此**改完代码块（`client.*.js`）必须顺手动一下入口**（例如 `touch client.js` 或
改一行注释），否则浏览器既不重载、旧版本缓存也还在：

```bash
touch client.js
```

**Host 半边是另一套机制**：profile 里装了 `dsh-dev-hmr`，它监听整棵插件源码树，保存
`index.js` 或任何 `host.*.js` 都会**热重载宿主插件**（同一个进程，不重启）。所以改完 Host
代码不用重启 `dsh web`；只有改了 `package.json` 的依赖关系、或新增一个包时才需要。

改动行为时请一并跑全部离线测试（零依赖，秒级）：

```bash
node test/layout-contract.mjs
node test/views-contract.mjs
node test/tint-contract.mjs
node test/font-contract.mjs
node test/save-contract.mjs
node test/staged-save-contract.mjs
node test/rename-contract.mjs
node test/drag-contract.mjs
node test/focus-contract.mjs
node test/preset-contract.mjs
node test/open-contract.mjs
node test/mcp-contract.mjs
node test/delete-contract.mjs
node test/menu-contract.mjs
node test/skill-contract.mjs
node test/fx-contract.mjs
node test/graph-contract.mjs
node test/dispatch-contract.mjs
node test/dispatch-batch-contract.mjs
node test/dispatch-restart-contract.mjs
node test/report-contract.mjs
node test/consult-contract.mjs
node test/control-contract.mjs
```

改到「光标归属」那块时，另外跑一遍真浏览器探针（需要 `google-chrome`，约十秒）：

```bash
node tools/browser-probe.mjs
```

改到「替换工作区」那块时，跑第三个真浏览器探针（同样需要 `google-chrome` 与 `dsh`，
约一分钟；`DSH_REPLACE_PROBE_URL` 可复用一个开着的服务）：

```bash
node tools/replace-probe.mjs
```

改到「拖动交换位置」那块时，跑另一个真浏览器探针（需要 `google-chrome` 与 `dsh`；
它会自己起一个独立的 web 服务，约两分钟）：

```bash
node tools/swap-probe.mjs                                  # 自己起服务
DSH_SWAP_PROBE_URL='http://127.0.0.1:PORT/?token=…' \
  node tools/swap-probe.mjs                                # 或复用已经开着的服务
```

想在**真实页面**上看这套行为，可以用另一个无头客户端点一遍（不影响自己开着的窗口）：
`dsh web --no-open --port 0` 会打印带令牌的 URL，把它交给无头 Chrome，然后
①切到平铺面板 ②点某个窗格标题栏里的工作区名 → 光标应当进那个窗格的输入框
③点标题栏的「分屏」按钮 → 焦点应当留在按钮上、不进输入框
④在窗格里拖选一段文字 → 选区必须还在（说明守卫给选区让路了）
⑤点当前窗格的关闭按钮 → 顶替它的窗格应当在下一帧接上光标
⑥按住某个窗格的标题栏拖到另一个窗格上松手 → 两格交换位置，且**两边的对话都不重开**
（交换前后各看一眼窗格里的消息还在不在、有没有闪出「正在打开会话…」）
⑦点某一格标题栏的「替换工作区」图标 → 第一级是「新建工作区…」+ 全部工作区（已铺开的
标「已打开」）；点一个工作区 → 第二级第一条是「新建会话」，下面是它的会话；选一个已有
会话 → **这一格的位置与大小都不变**，里面换成那个会话，其余格子一个像素都不动。
